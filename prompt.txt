## Mục tiêu lần này

Chỉ **đếm chính xác tập search key có thể dùng cho production locator từ index hiện tại**, rồi dùng số liệu benchmark đã có để ước tính kích thước production.

Không generate production locator.
Không tạo artefact remote mới.
Không redesign.

## 1. Giữ nguyên toàn bộ hệ thống hiện tại

## 2. Đếm key universe từ dữ liệu/index hiện có

Cần báo ít nhất 3 nhóm:

### A. Latin / Pāli / Sanskrit / romanized terms

Dùng nguồn vocabulary/search-key phù hợp hiện có trong index.

Ưu tiên:

```text
lemmas.lemma
```

Đếm:

```text
total rows
distinct non-empty keys
distinct normalized keys
```

Loại key CJK khỏi nhóm này.

Không tự tạo dictionary mới.

### B. Identifier keys

Dùng identifier thực tế hiện có, ưu tiên:

```text
records.work_id
```

Đếm:

```text
distinct original work_id
distinct normalized work_id
```

Nếu cùng identifier xuất hiện ở nhiều corpus thì báo thêm:

```text
distinct (corpus, work_id)
```

Nhưng production key count chính vẫn cần một con số distinct key rõ ràng.

### C. CJK search keys

Dùng **index CJK hiện có**, không lấy lại sample 5.000 record như benchmark.

Mục tiêu là đếm toàn bộ key CJK thực tế mà runtime locator có thể hỗ trợ.

Nếu CJK index hiện tại có bảng/index vocabulary rõ ràng, dùng trực tiếp.

Báo:

```text
distinct CJK keys
key length distribution
```

Tối thiểu:

```text
1-char
2-char
3-char
4+ char
```

Nếu index hiện tại chỉ chứa trigram hoặc một representation cụ thể thì ghi rõ chính xác.

**Không scan/generate một index CJK mới.**

Nếu không thể lấy một “production CJK key universe” có ý nghĩa từ index hiện tại mà không làm kiến trúc mới, hãy báo rõ và dừng phần CJK ở số liệu khả dụng nhất.

## 3. Dedupe giữa các nhóm

Báo:

```text
Latin distinct normalized keys
CJK distinct keys
Identifier distinct normalized keys
```

Sau đó tính:

```text
union total production keys
```

Nếu namespace khác nhau nên không dedupe xuyên nhóm, ghi rõ:

```text
production key namespace total
```

thay vì gộp sai semantics.

Ví dụ:

```text
terms/latin
terms/cjk
ids
```

## 4. Đếm key usability

Không cần chạy retrieval cho toàn bộ universe.

Nhưng báo tối thiểu các sanity checks:

- empty keys;

- duplicate normalized keys;
- identifier bị mất punctuation nếu normalize;
- số key có độ dài bất thường.

Không tự sửa dữ liệu trong task này.

## 5. Ước tính production locator size

Dùng **benchmark thực tế đã verify**:

```text
500 query
6,935,403 bytes
```

Nhưng không chỉ lấy một average duy nhất nếu có breakdown theo category.

Ưu tiên dùng category-specific bytes/query từ benchmark:

```text
Latin/romanized
CJK
Identifier
```

để estimate:

```text
estimated Latin bytes
estimated CJK bytes
estimated identifier bytes
estimated total production bytes
```

Báo cả:

```text
decimal MB
MiB
GiB nếu cần
```

Ngoài ra báo một range đơn giản:

```text
lower estimate
central estimate
upper estimate
```

Có thể dùng median / average / p95 benchmark để tạo range, miễn cách tính rõ ràng.

Không gọi đây là size chắc chắn.

## 6. Ước tính pointer count

Dùng benchmark category-specific pointer/query để ước tính:

```text
Latin pointer occurrences
CJK pointer occurrences
Identifier pointer occurrences
total pointer occurrences
```

Đây chỉ là extrapolation.

## 7. Ước tính generation cost đơn giản

Nếu có thể từ benchmark trước, dùng số đo generation:

```text
500 query
8 phút 36 giây
```

để ngoại suy tuyến tính thô:

```text
estimated generation time
```

Nhưng ghi rõ đây chỉ là rough extrapolation, không phải benchmark production thật.

Không tối ưu performance trong task này.
